# API приложения «Комментарии»

Инструкция для бэкенда. Клиент уже написан под этот контракт (`frontend/src/api.js`, `frontend/src/socket.js`, `frontend/src/thread.js`). `frontend_old` — только образец старой версии.

## 1. Общая схема

| Канал | Адрес | Для чего |
|---|---|---|
| GraphQL по HTTP | `POST /graphql/` | Все запросы данных и все изменения. REST нет |
| WebSocket | `/ws/comments/` | Клиент сообщает, что у него на экране, сервер шлёт события только об этой зоне |
| Статика | `/media/...` | Вложения. Nginx забирает их из бакета, бэкенд не участвует |

Бэкенд — Django в одном процессе ASGI: Strawberry (умеет `Upload` и multipart) и Channels. Слой Channels, капчи, лимиты с одного IP и видимые зоны живут в Redis, поэтому процессов может стать несколько.

Сокет работает на обычном JSON, а не на GraphQL Subscriptions: видимая зона часто меняется, и отправлять её одним сообщением проще, чем переподписываться.

## 2. Схема GraphQL

```graphql
scalar Upload

enum CommentOrdering {
  CREATED_AT_DESC    # по умолчанию
  CREATED_AT_ASC
  USERNAME_ASC
  USERNAME_DESC
  EMAIL_ASC
  EMAIL_DESC
}

enum AttachmentType {
  IMAGE
  TEXT
}

type Comment {
  id: ID!
  parentId: ID                      # null у комментария верхнего уровня
  rootId: ID                        # null у комментария верхнего уровня
  username: String!
  email: String!
  homePage: String!                 # "" если не указан
  text: String!                     # очищенный XHTML
  attachment: String                # "/media/attachments/2026/11/<uuid>.jpg" или null
  attachmentType: AttachmentType    # null, если вложения нет
  createdAt: String!                # ISO 8601 с часовым поясом
  replyCount: Int!                  # только прямые ответы
}

type CommentPage {
  count: Int!                       # всего комментариев верхнего уровня
  results: [Comment!]!              # не больше pageSize штук
}

type Captcha {
  key: String!
  image: String!                    # data:image/png;base64,... размером 160×56
}

type CreateCommentResult {
  comment: Comment!
  token: String                     # только если капчу решили в этом запросе
  tokenExpiresIn: Int               # секунды
}

input CommentInput {
  username: String!
  email: String!
  homePage: String!
  text: String!
  parentId: ID
  captchaKey: String                # null, если запрос пришёл с токеном
  captchaValue: String              # null, если запрос пришёл с токеном
}

type Query {
  comments(page: Int!, pageSize: Int!, ordering: CommentOrdering!): CommentPage!
  replies(parentId: ID!): [Comment!]!
  previewText(text: String!): String!
}

type Mutation {
  issueCaptcha: Captcha!
  createComment(input: CommentInput!, attachment: Upload): CreateCommentResult!
}
```

### Правила запросов

- **`comments`** возвращает только комментарии верхнего уровня. При равных значениях сортировки следующим ключом идёт `-id`, иначе расчёт страниц из раздела 6 разойдётся с выдачей. Размер страницы задаёт клиент: `pageSize` от 1 до 100, другое значение даёт ошибку `INVALID_PAGE_SIZE`. Страница за пределами списка даёт ошибку `PAGE_NOT_FOUND`, клиент тогда вернётся на первую.
- **`replies`** возвращает только прямые ответы на комментарий, по `created_at` от новых к старым. Весь тред одним запросом больше не загружается: каждый уровень запрашивается при раскрытии.
- **`previewText`** выполняет те же проверки текста, что и `createComment`, и возвращает очищенный HTML. Ничего не сохраняет.
- **`issueCaptcha`** — мутация, потому что создаёт запись. Капча живёт 5 минут и одноразовая: любая попытка её расходует. Капчи хранятся в Redis без записи на диск, поэтому после его перезапуска выданные становятся недействительными: клиент получит ошибку `captchaValue` и покажет новую.

Идентификаторы — всегда строки, и в GraphQL, и в сокете. Клиент сравнивает их строго.

### Проверка полей

| Поле | Правило |
|---|---|
| `username` | Обязательное, латиница и цифры, до 64 символов |
| `email` | Обязательное, корректный адрес, до 254 символов |
| `homePage` | Необязательное, `http://` или `https://`, до 200 символов |
| `text` | Обязательное, до 5000 символов |
| `parentId` | Существующий комментарий |
| `captchaValue` | Латиница и цифры, до 16 символов |

В `text` разрешены только теги `<a href title>`, `<code>`, `<i>`, `<strong>`. Теги должны быть правильно закрыты и вложены. Запрещены HTML-комментарии, декларации, самозакрывающиеся теги, вложенные друг в друга ссылки и незавершённый тег в конце текста. `href` начинается с `http://`, `https://` или `mailto:`. Клиентские правила лежат в `frontend/src/validation.js`, но решает всегда сервер.

Автор определяется парой `username` + `email`, запись в `comments_author` создаётся при первом комментарии. `homePage` берётся из этого первого комментария и потом не меняется: пара публична, поэтому чужой комментарий не должен подменять ссылку на всех старых.

### Токен вместо капчи

После решённой капчи `createComment` возвращает `token` и `tokenExpiresIn`. Токен привязан к паре `username` + `email`. Клиент шлёт его в заголовке `Authorization: Bearer <token>` и тогда не передаёт капчу. Токен живёт 1 час и не продлевается. Если токен просрочен или не подходит, сервер отвечает ошибкой `VALIDATION` с полем `captchaValue`, и клиент снова показывает капчу.

## 3. Ошибки

Ошибки приходят в стандартном поле `errors` ответа GraphQL. Клиент читает только первую из них и смотрит на `extensions`:

```json
{
  "data": null,
  "errors": [{
    "message": "Validation failed",
    "extensions": {
      "code": "VALIDATION",
      "fields": { "username": "Только латинские буквы и цифры." }
    }
  }]
}
```

| `code` | Когда | Что делает клиент |
|---|---|---|
| `VALIDATION` | Неверные данные в `createComment` или `previewText` | Показывает `fields` возле полей |
| `PAGE_NOT_FOUND` | Нет такой страницы | Открывает первую страницу |
| `INVALID_PAGE_SIZE` | `pageSize` вне диапазона | Показывает общую ошибку |
| `RATE_LIMITED` | Превышен лимит `createComment` или `issueCaptcha` с одного IP | Показывает `fields.rateLimit` как общую ошибку формы |
| Любой другой | Сбой сервера | Показывает общую ошибку |

Ключи `fields`: `username`, `email`, `homePage`, `text`, `captchaKey`, `captchaValue`, `attachment`. Значение — одна строка на русском, её видит пользователь. Сообщение с незнакомым ключом клиент покажет как общую ошибку формы: так приходит `parentId`, если комментария-родителя нет.

### Лимиты с одного IP

| Где | Лимит | Что происходит сверх него |
|---|---|---|
| `createComment` | 10 в минуту | Ошибка `RATE_LIMITED`, капча не расходуется |
| `issueCaptcha` | 30 в минуту, каждый алиас считается отдельно | Ошибка `RATE_LIMITED` |
| Все запросы к `/graphql/` и `/ws/` | 20 в секунду, всплеск до 100 | Nginx отвечает `429` без тела GraphQL, клиент показывает общую ошибку |

Счётчики первых двух лимитов общие для всех процессов backend, живут в Redis и сбрасываются при его перезапуске.

## 4. Загрузка файла

Без файла `createComment` — обычный JSON-запрос. С файлом клиент шлёт `multipart/form-data` по [спецификации GraphQL multipart request](https://github.com/jaydenseric/graphql-multipart-request-spec):

```
operations = {"query": "mutation ...", "variables": {"input": {...}, "attachment": null}}
map        = {"0": ["variables.attachment"]}
0          = <файл>
```

Заголовок `Authorization` передаётся так же, как и в JSON-запросе.

## 5. Вложения

Файл обрабатывается прямо внутри `createComment`, фоновых задач нет. Порядок такой:

1. Проверить поля и капчу.
2. Проверить и обработать файл.
3. Загрузить результат в бакет.
4. Сохранить комментарий в базе.
5. После фиксации транзакции разослать события.

Если файл не прошёл проверку или бакет не ответил, комментарий не создаётся. Ошибка возвращается в поле `attachment`.

Все проверки клиента повторяются на сервере, потому что браузерные проверки легко обойти.

### Изображения

- Форматы JPG, PNG, GIF определяются по содержимому, а не по расширению.
- Лимит 5 МБ и 20 Мп на исходный файл.
- Учитывается ориентация из EXIF.
- Картинка вписывается в 320×240 с сохранением пропорций и никогда не увеличивается.
- Хранится только уменьшенная версия, оригинал не сохраняется.
- PNG остаётся PNG. Анимация GIF сохраняется: каждый кадр уменьшается отдельно.
- У GIF не больше 200 кадров и не больше 200 Мп на все кадры вместе: маленький файл может распаковаться в огромный объём данных.

### Файлы `.txt`

- Расширение `.txt`, лимит 100 КБ.
- Содержимое — корректный UTF-8.
- Нет управляющих символов: разрешены только `\t`, `\n`, `\r`, `\f`.
- Файл не пустой и не состоит из одних пробелов.
- BOM в начале файла удаляется, остальное хранится без изменений.
- HTML внутри файла допустим: клиент показывает его как обычный текст.

### Хранение

- Путь в бакете: `attachments/ГГГГ/ММ/<uuid>.<расширение>`.
- В `Comment.attachment` возвращается ссылка `/media/<путь>`. Прямые ссылки на бакет заблокирует CSP клиента.
- `Content-Type` объекта: `image/jpeg`, `image/png`, `image/gif` или `text/plain; charset=utf-8`.
- Настройки подключения: `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`. В boto3 для OCI нужны `addressing_style="path"`, `signature_version="s3v4"` и `request_checksum_calculation="when_required"`.

## 6. WebSocket

Соединение анонимное. Клиент подключается к `/ws/comments/`, сразу отправляет видимую зону и повторяет отправку при каждом её изменении. Новое сообщение полностью заменяет предыдущее.

### Клиент → сервер

```json
{
  "type": "viewport",
  "page": 3,
  "pageSize": 25,
  "ordering": "CREATED_AT_DESC",
  "thread": "123",
  "branches": [
    { "id": "123", "level": 0 },
    { "id": "456", "level": 1 }
  ]
}
```

| Поле | Значение |
|---|---|
| `page`, `pageSize`, `ordering` | Открытая страница, её размер и сортировка таблицы |
| `thread` | Раскрытая ветка: id комментария верхнего уровня или `null` |
| `branches` | Раскрытые комментарии: прямые ответы на них видны на экране. `level` — глубина этого комментария, у верхнего уровня 0 |

Клиент раскрывает одну ветку за раз. Пока ветка открыта, её корень всегда есть в `branches` с уровнем 0. Когда ветка закрыта, `branches` пуст.

Сервер проверяет сообщение: `page` ≥ 1, `pageSize` от 1 до 100, `ordering` из списка, id — числа, в `branches` не больше 200 записей. Неверное сообщение игнорируется, и в силе остаётся прошлая зона.

### Сервер → клиент

```json
{ "type": "comment.created", "id": "789", "parentId": "456", "rootId": "123" }
{ "type": "comment.replyCount", "id": "456", "replyCount": 4 }
```

| Событие | Реакция клиента |
|---|---|
| `comment.created` c `parentId: null` | Перезапрашивает текущую страницу со случайной задержкой до секунды. События за это время объединяются в один запрос |
| `comment.created` с `parentId` | Перезапрашивает `replies(parentId)` |
| `comment.replyCount` | Обновляет счётчик на месте, без запроса |

### Кому что отправлять

Сервер помнит, что видит каждое соединение. При каждом сообщении `viewport` он:

- записывает `page`, `pageSize` и `ordering` в словарь активных соединений по `channel_name`;
- переводит соединение в группы Channels `branch.<id>`, по одной на каждую запись `branches`.

При отключении запись удаляется. Словарь живёт в Redis и общий для всех процессов backend. Процесс, который упал, не может удалить свои записи, поэтому каждый процесс раз в 10 секунд отмечается в Redis, а записи процесса, который не отмечался минуту, удаляют остальные. Клиенты упавшего процесса переподключаются и сразу присылают `viewport`.

Страницу `X` у открытых таблиц сервер находит так:

1. Собирает из словаря сочетания `ordering` и `pageSize`, которые сейчас открыты.
2. Для каждой такой сортировки один раз считает позицию `X`, а из неё страницу для каждого открытого размера.
3. Шлёт событие напрямую по `channel_name` тем соединениям, у которых совпали `ordering`, `pageSize` и `page`.

После создания комментария `C` с родителем `P` сервер делает следующее.

**`C` верхнего уровня.** Находит страницу `C` и шлёт туда `comment.created`.

**`C` — ответ.**
1. Шлёт `comment.created` в `branch.<P>`.
2. Шлёт `comment.replyCount` с новым значением для `P` туда, где виден сам `P`:
   - если `P` верхнего уровня, то на страницу `P`, найденную тем же способом;
   - иначе в `branch.<родитель P>`.

Страница считается так: `позиция // pageSize + 1`, где позиция — число комментариев верхнего уровня, стоящих раньше в этой сортировке.

### Примеры

| У клиента открыто | Новый комментарий | Что придёт |
|---|---|---|
| Страница 1, `CREATED_AT_DESC` | Верхнего уровня | `comment.created` |
| Страница 3, `CREATED_AT_DESC` | Верхнего уровня | Ничего |
| Страница 1, строка 123 в таблице, ветка закрыта | Ответ на 123 | `comment.replyCount` |
| Ветка 123 | Ответ на 123 | `comment.created` |
| Ветка 123, виден ответ 456, он не раскрыт | Ответ на 456 | `comment.replyCount` |
| Ветка 123, раскрыт 456 | Ответ на 456 | `comment.created` |
| Страница 1, ветка 123 закрыта | Ответ на 456 | Ничего |

### Что клиент намеренно не узнаёт

Клиент на дальней странице не получает события о комментарии с другой страницы. На экране у него ничего не меняется, хотя в базе строки этой страницы уже сдвинулись, а счётчик в шапке устарел. Новый порядок строк и счётчик он увидит при следующей загрузке страницы.

После обрыва клиент сам перезапрашивает страницу и все раскрытые ветки, поэтому хранить пропущенные события не нужно.

## 7. Изменения в базе

- Столбец `attachment_status` и индекс `comments_co_attachm_e01fd7_idx` удалены: фоновой обработки нет, вложение всегда готово.
- Таблица `comments_captcha` удалена: капчи живут в Redis.
- `replyCount` — это число строк с `parent_id = id`. Он считается подзапросом по индексу `comments_co_parent__2efacb_idx` и только для строк страницы: сначала выбираются их `id`, потом сами строки. Иначе при сортировке по `username` и `email` MySQL выполняет подзапрос для всех комментариев верхнего уровня.
- `username` и `email` автора скопированы в `comments_comment`, и для каждой сортировки по ним есть свой индекс вместе с `parent_id` и `-id`: без копии MySQL соединял все комментарии верхнего уровня с авторами, и такая страница стоила около 47 мс против 14 мс по дате. Пара автора не меняется, поэтому копию не нужно обновлять.

## 8. Что изменилось по сравнению со старым API

| Старый REST | Новый GraphQL |
|---|---|
| `GET /api/comments/?page=&ordering=` | `query comments` |
| `GET /api/comments/<id>/thread/` | `query replies`, по одному уровню |
| `POST /api/comments/` | `mutation createComment` |
| `POST /api/comments/preview/` | `query previewText` |
| `GET /api/captcha/` | `mutation issueCaptcha` |
| Ошибки 400 и 404 | `errors[].extensions` |
| Поля в `snake_case` | Поля в `camelCase` |
| Событие `comment.updated`, статусы `pending` и `failed` | Убраны |
| Сокет рассылал все события всем | Сервер фильтрует по видимой зоне |
