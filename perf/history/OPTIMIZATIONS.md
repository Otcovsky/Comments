## 0. Исходный код

Прогон `2026-11-03_0823_baseline-v1`, подробно — в [BASELINE.md](BASELINE.md).

Узкое место: MySQL (154% CPU из 200%) на запросе списка `GET /api/comments/`. `annotate(reply_count=Count("thread_comments"))` присоединял к 10 000 корневых комментариев все 50 000 ответов и группировал их во временной таблице до `LIMIT 25`, а `count()` пагинатора повторял тот же JOIN с GROUP BY. Около 130 тысяч прочитанных строк на каждый список, и 10 вкладок повторяют его на каждый новый комментарий.

## 1. Число ответов подзапросом

Прогон `2026-11-03_0913_subquery-count`, коммит `2118fee`, файл `backend/comments/views.py`.

**Что сделано.** `Count("thread_comments")` заменён коррелированным подзапросом `SELECT COUNT(*) … WHERE root_id = comment.id`. Его MySQL выполняет только для 25 строк страницы, а из `count()` Django его убирает, остаётся `COUNT(*) WHERE parent_id IS NULL`. Миграции нет, запросов на эндпоинт по-прежнему 2.

**Отдельно на MySQL** (60 000 комментариев, страница + count): сортировка по дате 184 → 3,6 мс, обращений к строкам и индексам 232 тыс. → 10 тыс.; по `username` 187 → 85 мс (сортируются все 10 000 корневых, подзапрос считается для каждого).

**Результат.**
- `load`: SLO выполняется впервые, all p95 2256 → 113 мс, `list p95` 2657 → 139 мс, `reload p95` 2908 → 229 мс, `visible p95` 3073 → 259 мс; db CPU 154% → 21%, временных таблиц на диске 48 → 0.
- Ёмкость 12 → 48 итераций/с.
- `upload` без изменений (этот код не затронут).
- Данные по-прежнему свежие и правильные: `content ok`, `fresh list`, `fresh thread` — 100%.
- Хуже стал только `reload-thread p95` (99 → 114 мс, +15%), в пределах обычного разброса редких запросов.

**Следующее узкое место.** На 48 итерациях/с backend (один процесс daphne) занят на 73% в среднем и до 89%, то есть почти одно ядро, база на ~98% — в основном `COUNT(*)` по 10 000 записей индекса на каждый список. На 56 итерациях/с p95 — 8,7 с. Кандидаты: кэш первой страницы и `count` с инвалидацией по `comment.created`, несколько процессов backend, фронтенд без перезагрузки списка на каждое событие.

## 2. Кэш в Redis

Прогон `2026-11-03_1146_redis-cache-split`, коммиты `343203b` и `d6428a5`, файлы `backend/comments/caching.py`, `views.py`, `docker-compose.yml` (сервис `redis:7.4-alpine`, без сохранения на диск, 128 МБ, `allkeys-lru`).

**Что сделано.** Страницы списка и ветки отдаются из Redis, повторный запрос не обращается к базе. Ключи содержат поколения, которые запись меняет после коммита, поэтому запрос, прочитавший базу до записи и сохранивший результат позже, пишет под ключом, который уже никто не читает: `fresh list` и `fresh thread` остаются 100%. Сброс выполняется до рассылки события по WebSocket, так что вкладки перезагружают уже свежие данные. Страницы хранятся под поколением корневых комментариев, а счётчики ответов отдельно, под поколением ответов: ответ (половина записей) стоит одного запроса `COUNT … WHERE root_id IN (25 id) GROUP BY root_id` по индексу, а не пересборки страницы с `COUNT(*)` по 10 000 корневых. Комментарий сбрасывает только свою ветку, остальные ветки остаются в кэше. Запросов на холодный список по-прежнему 2, на повторный 0.

**Промежуточный вариант** (прогон `2026-11-03_1043_redis-cache`, коммит `343203b`, в `chain.txt` не входит): одно поколение списка на любой новый комментарий. На 48 итерациях/с это около 6 сбросов в секунду, страницы почти не успевали попадать в кэш (за ступень больше 1000 ключей списка, большинство ни разу не прочитано): `load` all p95 113 → 106 мс, db CPU 21% → 18%, `rows read / request` −19%, ёмкость без изменений.

**Результат** (относительно шага 1).
- `load`: all p95 113 → 102 мс, p99 193 → 164 мс, `list p95` 139 → 110 мс; db CPU 21% → 13%, строк на запрос 21 054 → 11 124, полных сканов −57%; `app CPU` −20%.
- Ёмкость по-прежнему 48 итераций/с, но на этой ступени all p95 472 → 360 мс, `list p95` 621 → 470 мс, `create p95` 333 → 201 мс, db CPU 98% → 88%. На 56 итерациях/с SLO не выполняется (p95 9,2 с).
- `upload` без изменений.
- Хуже: `reload-thread p95` 114 → 161 мс (+42%) и `visible p50` 136 → 150 мс. Оба варианта кэша дали одно и то же, так что это, скорее всего, не разброс; причина пока не найдена (запрос редкий, на одну перезагрузку ветки приходится промах и три обращения к Redis).

**Следующее узкое место.** На 48 итерациях/с backend — один процесс daphne, синхронные view которого выполняются по одному в общем потоке, — занят на 72% в среднем и до 92%, база на 88%. В базе остаются промахи страниц после каждого нового корневого комментария (около 3 в секунду): каждый снова считает `COUNT(*)` по 10 000 записей индекса, а сортировки по `username`/`email` сортируют все корневые. Кандидаты: общее число корневых комментариев отдельно от страниц (оно меняется на единицу, его можно не пересчитывать), несколько процессов backend с общим channel layer в Redis (шаг Events), фронтенд без перезагрузки списка на каждое событие.

## 3. События и channel layer в Redis

Прогон `2026-11-03_1319_events-redis-layer`, коммиты `c9a1c44` и `646d62e`, файлы `backend/comments/events.py`, `apps.py`, `serializers.py`, `admin.py`, `config/settings.py`, `management/commands/startup.py`, `docker-compose.yml`.

**Что сделано.** Сохранение комментария публикует `CommentCreated`, новый адрес сайта автора и изменения в админке — `CommentsChanged`. После коммита шина передаёт событие подписчикам по порядку: кэш, затем WebSocket; сбой подписчика пишется в лог и не мешает остальным. Channel layer перенесён из памяти процесса в Redis (`channels_redis.core.RedisChannelLayer`, отдельная база Redis), чтобы события доходили до клиентов всех копий backend. Число копий задаёт `BACKEND_REPLICAS`; миграции и `collectstatic` копии выполняют по очереди под именованной блокировкой MySQL (`manage.py startup`). Здесь работает 1 копия.

**Результат** (относительно шага 2).
- `load` без изменений: all p95 102 мс, `list p95` 110 мс, `visible p95` 259 мс, доставка по WebSocket 100%; `create p95` 99 → 82 мс, `reload-thread p95` 161 → 108 мс.
- Ёмкость 48 → 40 итераций/с. Канал через Redis стоит backend нескольких процентов CPU (на 40 итерациях/с backend 59% → 63%, p95 180 → 192 мс), а на 48 итерациях/с хост уже был на пределе (простаивал ~10%), поэтому SLO нарушился (p95 557 мс). Это цена, которую одна копия платит за возможность нескольких.
- `upload` без изменений по задержкам; `rows read / request` 290 → 398 (+37%, в абсолютных числах около 100 строк на запрос), причина не выяснена.

## 4. Две копии backend

Прогон `2026-11-03_1408_events-2-replicas`, на сервере `BACKEND_REPLICAS=2` в `.env`, коммит `a37a941` (`perf/remote/app.sh`).

**Что сделано.** Две копии daphne за nginx, который распределяет запросы и WebSocket-подключения по DNS Docker. Вместе с этим исправлена подготовка прогона: `perf_reset` ждал первого ответа nginx, а вторая копия в этот момент ещё ждала блокировку при старте, поэтому все WebSocket-клиенты подключались к первой и оставались там весь прогон. Теперь `reset` ждёт ответа каждой копии и одного обновления DNS в nginx; в smoke подключения делятся 10/10, доставка 100%.

**Результат** (относительно шага 3).
- `load`: all p95 по-прежнему 102 мс, p50 14,8 → 13,3 мс, `visible p95` 259 → 231 мс, `reload p95` 231 → 217 мс, `thread p95` 30 → 25 мс. Хуже `attach p95` (257 → 221 мс, но 161 мс на шаге 2; запрос редкий, в `upload` без изменений).
- Ёмкость 40 → 48 итераций/с, то есть та же, что до событий. На 48 итерациях/с p50 63 → 42 мс относительно шага 2, но p95 почти тот же (360 → 376 мс), `list p95` 470 → 578 мс.
- Память: вторая копия добавляет около 90 МБ.

**Следующее узкое место.** Процессор хоста: на 48 итерациях/с MySQL занимает 89%, обе копии backend вместе 77%, хост простаивает 9,6% из 2 ядер. Вторая копия убирает очередь в одном потоке daphne (медиана и `visible` лучше), но ёмкость упирается в общий CPU, и в основном в базу. Кандидаты: вынести MySQL с сервера приложения (Oracle Cloud MySQL HeatWave, пункт ТЗ про облако), отдельный кэш общего числа корневых комментариев (каждый промах страницы считает `COUNT(*)` по 10 000 записей), фронтенд без перезагрузки списка на каждое событие. Очередь (следующий пункт ТЗ) снимет с запроса обработку вложений, но не нагрузку на базу.

## 5. Число ответов по странице, общее число корневых в кэше

Прогон `2026-11-03_1759_reply-counts-per-page`, коммит `47643c1`, файлы `backend/comments/views.py`, `caching.py`, `serializers.py`.

**Причина.** При промахе страницы с сортировкой по `username`/`email` MySQL выполнял подзапрос `reply_count` для всех 10 000 корневых комментариев: JOIN с автором и сортировка требуют сначала собрать все строки, и только потом сортировать и брать `LIMIT 25`. На данных сервера одна такая холодная страница читала 80 677 строк (10 165 полного прохода, 20 324 по ключу, 70 519 по индексу ответов), страница по дате — около 10 300, почти всё на `COUNT(*)` пагинатора. Этим же объясняется рост `rows read / request` в `upload` на шаге 3 (290 → 398): в основной фазе `upload` нет чтений списка, почти все строки читают ~24 запроса `setup` и прогрева, и на шаге 3 среди них оказался на одну холодную страницу с сортировкой по автору больше (+80 037 строк за прогон, ровно её цена).

**Что сделано.** Запрос страницы больше не считает ответы: `count_replies()` считает их для 25 строк страницы при каждом промахе, в том числе для номеров страниц мимо кэша (`?page=last`). Пагинатор берёт общее число корневых комментариев из кэша, оно хранится один раз на поколение корневых, а не пересчитывается `COUNT(*)` для каждой страницы и сортировки. Холодная страница — 3 запроса (общее число, страница, ответы), 2 после того, как общее число в кэше; отдельно на MySQL страница по автору стоит около 20 500 строк вместо 80 700.

**Результат** (относительно шага 4).
- `load`: all p95 102 → 70 мс, p99 168 → 128 мс, `list p95` 114 → 79 мс, `reload p95` 217 → 182 мс, `ws delivery p95` 120 → 99 мс, `visible p95` 231 → 220 мс; db CPU 11,9% → 9,6%, строк на запрос 9 884 → 4 468.
- Ёмкость 48 → 56 итераций/с. На 48 итерациях/с all p95 376 → 140 мс, `list p95` 578 → 159 мс, db CPU 89% → 55%, хост простаивает 23,5% вместо 9,6%. На 56 итерациях/с (раньше p95 10,7 с при db CPU 101%) p95 303 мс, db CPU 68%; на 64 SLO не выполняется (p95 8,7 с).
- `upload` без изменений по задержкам, `rows read / request` 399 → 63: холодные страницы прогрева стали дешёвыми.
- Хуже: `reload-thread p95` 94 → 185 мс, но на прогон таких запросов 5–12, и между `load-a` и `load-b` он сам расходится на 20%; `create p95` 79 → 86 мс (+8%, в пределах разброса редких запросов). `full scans / request` 0,18 → 0,21: страница по автору теперь обычный полный проход вместо временной таблицы, так её считает `Select_scan`.

**Следующее узкое место.** Процессор хоста, но теперь больше его занимает backend: на 56 итерациях/с обе копии вместе 94%, MySQL 68%, nginx 6%, хост простаивает 8,7%. Кандидаты: фронтенд без перезагрузки списка на каждое событие (меньше запросов на каждый комментарий), вынести MySQL с сервера приложения (Oracle Cloud MySQL HeatWave) и тем освободить процессор для backend, защита от одновременных промахов страницы после нового корневого комментария.

## 6. Очередь задач: картинки в Celery

Прогон `2026-11-03_1919_celery-queue`, коммит `b811cc5`, файлы `backend/comments/attachments.py`, `tasks.py`, `apps.py`, `caching.py`, `broadcast.py`, `config/celery.py`, `config/settings.py`, `docker-compose.yml`, фронтенд (`updates.js`, `CommentCard.jsx`, `App.jsx`, `Thread.jsx`), `perf/k6/main.js`.

**Что сделано.** В запросе остались только проверки по заголовку картинки (формат, размер, разрешение); комментарий сохраняется с итоговым путём файла и `attachment_status: "pending"`, исходник ждёт в томе `pending`, который nginx не раздаёт. Подписчик `CommentCreated` ставит задачу в Celery, воркер (сервис `worker`, 1 процесс) перекодирует картинку, ставит `ready` или `failed` и публикует `AttachmentProcessed`: кэш сбрасывает ветку комментария (и страницы списка, если он заглавный), клиенты получают `comment.updated` и подставляют картинку на место без перезагрузки. Брокер — отдельный Redis (`broker`): без вытеснения ключей и с журналом на диске, в отличие от Redis кэша. `perf_reset` очищает очередь и файлы `pending`. В k6 опрос готовности файла идёт раз в 50 мс вместо 250 мс, 404 до готовности не считается ошибкой, а `thread` не скачивает картинки со статусом `pending`, как и фронтенд; на коде без очереди поведение теста не меняется, поэтому версия набора та же.

**Результат** (относительно шага 5).
- `upload`: `attach p95` 113 → 45 мс (−60%), all p95 110 → 41 мс; картинка готова через `attachment ready p95` 104 мс после ответа. Перекодирование переехало из backend (CPU 9,8% → 7,0%) в воркер (6,3%), всё приложение 14,0% → 19,2%: воркер, второй Redis и запросы воркера к базе (`SQL queries / request` 14,8 → 18,2: выборка, обновление и служебные команды нового соединения на каждую задачу, `CONN_MAX_AGE = 0`).
- `load` хуже: all p95 70 → 82 мс (+17%), `list p95` 79 → 86 мс, `visible p95` 220 → 246 мс; backend CPU тот же (12,0%), db CPU +4%, app CPU +7%. `attach` здесь 2% итераций, и на задержки самой загрузки очередь почти не влияет (183 → 214 мс, разброс редкого запроса).
- Ёмкость 56 → 48 итераций/с (на одну ступень). На 48 итерациях/с app CPU 141% → 157% (backend 78 → 82, MySQL 55 → 63, воркер 2,4), хост простаивает 16,8% вместо 23,5%, `list p95` 159 → 306 мс; на 56 SLO нарушен (p95 2,5 с, MySQL 82%).

**Почему хуже.** Перекодирование картинки стоит мало (в `step` воркер занят 2–3%), а очередь добавляет работу: готовая картинка заглавного комментария сбрасывает страницы списка второй раз (после самого комментария), и их пересобирают с базы. На 48 итерациях/с таких сбросов около 0,4 в секунду к 2,4 от новых заглавных комментариев (+17%), отсюда рост `list p95` и CPU MySQL. Плюс у каждой задачи новое соединение с MySQL и публикация в брокер.

**Следующее узкое место.** То же, что на шаге 5: процессор хоста (backend и MySQL). Для самой очереди: не сбрасывать страницы списка, когда картинка готова (в строке списка от вложения видна только отметка, а статус можно накладывать на страницу так же, как число ответов), держать соединение воркера с базой открытым (`CONN_MAX_AGE` для воркера).

## 7. Готовая картинка не сбрасывает страницы списка

Прогон `2026-11-03_2048_queue-list-overlay`, коммит `cc294d0`, файлы `backend/comments/caching.py`, `apps.py`, `serializers.py`.

**Что сделано.** Готовая картинка заглавного комментария больше не меняет поколение корневых комментариев. Поля её вложения кладутся в кэш по id комментария (`comments:attachment:<id>`, живут дольше страниц) и накладываются при чтении на строки закэшированной страницы, которые там ещё `pending`, как число ответов. Сбрасывается только ветка комментария. Страница без строк `pending` (почти всегда) читается так же, как раньше, без лишних обращений к кэшу.

В этот прогон вошла и настройка `CONN_MAX_AGE` для воркера, чтобы он не открывал новое соединение с MySQL на каждую задачу. Она ни на что не повлияла: Celery сам закрывает соединения Django до и после каждой задачи, если не задан `CELERY_DB_REUSE_MAX`, и на сервере у воркера между задачами действительно нет соединения. Настройка удалена следующим коммитом, поведение кода от этого не меняется. Задач меньше одной в секунду, поэтому переиспользование соединения много бы не дало.

**Результат** (относительно шага 6).
- Ступень 48 итераций/с: `list p95` 306 → 224 мс, all p95 227 → 186 мс, MySQL 62,7% → 58,7%, хост простаивает 18,4% вместо 16,8%. До очереди (шаг 5) было 159 мс, 140 мс, 55,2% и 23,5%.
- Ёмкость та же, 48 итераций/с: на 56 SLO нарушен (p95 2,0 с; на шаге 5 было 303 мс). Там app CPU 190% против 172% на шаге 5: MySQL 79 против 68, backend 95 против 94, воркер 3,8, Redis кэша и брокер вместе около 5 против 4.
- `load` и `upload` без заметных изменений: all p95 82 → 84 мс, `list p95` 86 → 93 мс (+9%, но CPU и строки на запрос те же), MySQL 9,9% → 9,4%; в `upload` `attach p95` 45 → 51 мс, файл готов через 104 мс.

**Почему ёмкость не вернулась.** На шаге 5 ступень 56 уже шла на пределе: хост простаивал 8,7%. Очередь добавляет около 5% CPU (воркер, брокер, публикация задачи и событие `comment.updated` на 50 подключений), и этого хватает, чтобы на 56 процессор кончился. Дальше растут промахи кэша, которые приходят одновременно (MySQL 68% → 79%, строк на запрос +14%), и задержки уходят за SLO. Перекодирование картинки на самой загрузке теперь не видно (`attach p95` −55%), но в смеси `step` загрузок 2%, поэтому выигрыш меньше накладных расходов. Остаток задержек в `load` (all p95 70 → 84 мс относительно шага 5 при том же CPU), вероятно, в том, что воркер жмёт картинку сразу после события `comment.created`, когда все вкладки разом перезагружают список, а раньше это происходило до события. Отдельно это не проверялось.

**Следующее узкое место.** Процессор хоста, как на шаге 5. Кандидаты: защита от одновременных промахов страницы после нового корневого комментария (на пределе MySQL читает на 14% больше строк), фронтенд без перезагрузки списка на каждое событие, вынести MySQL с сервера (Oracle Cloud MySQL HeatWave), понизить приоритет воркера (`cpu_shares`), чтобы он уступал процессор запросам.

## 12. Пул соединений и очистка капчи без дедлоков

На 72 один замер не прошёл (p95 412 мс, 1 пропущенная итерация), второй прошёл (p95 339 мс), p99 1,2–1,9 с. Устойчиво ёмкость 56, на 64–72 результат плавает.

Процессор сервера приложения тоже не на пределе, поэтому возможны задержки на стороне базы, а её CPU не измерен: его нужно брать из мониторинга Oracle.

**Следующее узкое место.** На 56 итерациях/с обе копии backend вместе 94%, хост простаивает 40%. Поэтому при обычной работе предел задаёт backend, а провалы на 64 и выше требуют данных с базы.

## 13. Вложения в Oracle Object Storage

Прогон `2026-11-05_1318_object-storage`, коммиты `9d14ed3`, `6cb4ce3`, файлы `backend/comments/storage.py`, `tasks.py`, `tests.py`, `config/settings.py`, `frontend/nginx.conf`, `Dockerfile`, `perf/remote/app.sh`. Отдельная правка после прогона, `c9b4c09`, в набор не вошла.

**Что сделано.** Готовые вложения хранятся в публичном бакете `comments-app-files` через S3-совместимый API Oracle (`django-storages`). Ссылки остаются вида `/media/...`: политика CSP страницы разрешает только свой домен. nginx ищет файл в томе `media`, затем берёт из бакета и кэширует ответы 200 на 7 дней. Ответы 404 не кэшируются: иначе картинка, которую ещё обрабатывает воркер, оставалась недоступной. На smoke до этой правки `attachment ready` был 0%, после неё 100%. Кэш nginx очищается в `reset`, иначе прогон начинался бы тёплым. В бакет перенесено 453 файла, расхождений в размерах нет. Локальной MySQL отключены бинарные логи (`--skip-log-bin`), на прогоны с HeatWave это не влияет.

**Результат** (относительно шага 12).
- `load`: all p95 82,0 → 76,0 мс, `list p95` 95,4 → 86,9 мс, `visible p95` 198 → 195 мс в пределах разброса; ошибок нет, `attachment ready` и `media failed` без потерь.
- Цена первого показа: `media p95` 1,52 → 39,7 мс, в `upload` 1,32 → 48,3 мс. Файл не из кэша nginx идёт в бакет.
- Цена записи: `attachment ready p95` 150 → 370 мс, в `upload` 104 → 219 мс.
- `attach p95` 150 → 274 мс, в `upload` 42,0 → 65,5 мс, при этом медиана в `upload` 33,5 → 35,1 мс. Рос только хвост: `.txt` писался в бакет прямо в запросе, а это 15% загрузок. Запись небольшого файла занимает около 29 мс, холодная до 412 мс.
- Память: backend 215 → 247 МиБ, worker 130 → 159 МиБ, в `upload` worker 131 → 195 МиБ. CPU backend почти не изменился, `nginx CPU` в `upload` 0,40 → 1,69%.
- Запись на диск в `load` 39,8 → 23,8 КиБ/с. Том `media` больше не растёт, но кэш nginx занимает до 1 ГиБ диска.
- Ёмкость 64 итерации/с, но устойчивой остаётся прежняя оценка: на шаге 12 результат на 64–72 плавал, а бакет нагрузку на backend не снижает. На 56 итерациях/с p99 снова поднимался до 1,56 с, на 80 SLO нарушен (p95 527 мс). Набор сделал порядка 8 тысяч запросов к бакету (оценка по логам nginx и числу файлов).

**Что нашлось.** Ошибка записи `.txt` в запросе не перехватывалась: при недоступном бакете комментарий не создавался. Правка `c9b4c09` отправляет `.txt` через воркер, как картинки, с повторами при сбое. Набор на ней не снимался. Проверено 79 тестами, smoke `2026-11-05_1615_txt-worker` (SLO пройден, ошибок нет) и настоящей загрузкой файла в cp1251 через сайт: ответ за 41 мс со статусом `pending`, затем файл в UTF-8 и статус `ready`.

**Что осталось.** Причина всплесков p99 на верхних ступенях не найдена, CPU базы нужно брать из мониторинга Oracle. Лимит запросов к бакету на тарифе официально не проверен. Бэкенд и воркер должны работать на одной машине: исходные файлы ждут в томе `pending`.

**Следующее узкое место.** Без изменений: при обычной работе предел задаёт backend (шаг 12).
