# Комментарии

Приложение комментариев с ветками ответов, вложениями и живыми обновлениями.

| Папка | Что внутри |
|---|---|
| `frontend/` | Клиент на React и Vite, конфигурация nginx, Dockerfile |
| `backend/` | Сервер на Django: GraphQL, WebSocket, вложения |
| `docs/api.md` | Контракт API: GraphQL, WebSocket, правила для вложений |
| `docs/db_schema.sql` | Схема базы данных |
| `perf/` | Нагрузочные тесты на k6, см. `perf/README.md` |

## Запуск фронтенда

```bash
cd frontend
npm ci
npm run dev
```

Клиент открывается на `http://localhost:5173`. Запросы к `/graphql/`, `/ws/` и `/media/` Vite передаёт на адрес из `BACKEND_URL`, по умолчанию `http://127.0.0.1:8000`.

## Бэкенд

Два процесса uvicorn, по одному на ядро сервера (`WEB_CONCURRENCY`; `BACKEND_WORKERS=1` в `comments.env` оставляет один). Слой Channels, видимые зоны клиентов, капчи, лимиты с одного IP и число корневых комментариев живут в Redis (`backend/comments/shared.py`), поэтому процессы видят одно и то же: капчу, выданную одним, проверяет другой, а событие из одного доходит до сокетов другого. Страницы списка, ветки и строки комментариев кешируются в Redis (`backend/comments/cache.py`): строки не меняются, а новый комментарий сдвигает версию только того, что он меняет — список корневых или ветку своего родителя. События о новых комментариях рассылает воркер Celery (сервис `worker`, задачи в `backend/comments/tasks.py`) из очереди в RabbitMQ: веб-процессы только ставят задачу, а если брокер недоступен, рассылают сами. Он же удаляет из бакета файл комментария, который не удалось сохранить. Клиенты Redis ждут подключения и ответа по секунде и повторяют запрос один раз (`REDIS_OPTIONS` в `config/settings.py`). Без Redis список и ответы читаются как обычно (число корневых считается в базе), лимиты с одного IP не действуют, писать можно только с токеном автора: капчу не выдать и не проверить. Видимые зоны каждый процесс помнит сам и возвращает в Redis с ближайшим heartbeat, раз в 10 секунд. База и файлы блокируют поток, так что вся такая работа идёт через постоянные потоки из `backend/comments/pools.py`.

Настройки приходят из окружения: `DB_*` и `S3_*` как в `docs/api.md`, а также `DJANGO_SECRET_KEY` и `DJANGO_ALLOWED_HOSTS` (через запятую, для проверки Origin у сокета). Адрес Redis (`REDIS_URL`) задаёт `docker-compose.yml`. Для RabbitMQ в `comments.env` нужен `RABBITMQ_PASSWORD`, имя пользователя по умолчанию `comments` (`RABBITMQ_USER`). Только на время нагрузочных тестов задают `CAPTCHA_TEST_ANSWER`, `RATE_LIMIT_EXEMPT` и `DB_POOL_REPORT`, см. `perf/README.md`.

## Тесты

Тестам нужна своя база, а пользователю облачной MySQL её создавать нельзя, поэтому они поднимают временную MySQL в контейнере:

```bash
docker compose -f docker-compose.test.yml run --rm --build tests
```

## Запуск на сервере

Рядом с папкой проекта лежит `comments.env`. Из папки проекта:

```bash
docker compose --env-file ../comments.env up -d --build
```

Миграции применяет сервис `migrate` один раз перед стартом бэкенда. Снаружи открыт только порт 80, порты бэкенда, Redis и RabbitMQ закрыты.
