# Комментарии

SPA-приложение комментариев: ветки ответов любой глубины, картинки и текстовые файлы во вложениях, новые комментарии появляются у всех открытых вкладок без перезагрузки.

Развёрнутая версия: http://89.168.107.87/

## Возможности

- **Форма комментария.** User Name (латиница и цифры), E-mail, Home page (необязательно), CAPTCHA-картинка и текст. Поля проверяются и в браузере, и на сервере, а решает всегда сервер. Имя, e-mail и адрес страницы форма запоминает до следующего раза.
- **Разметка в тексте.** Разрешены только `<a href="" title="">`, `<code>`, `<i>` и `<strong>`. Для них есть панель кнопок [i] [strong] [code] [a]. Сервер проверяет, что теги закрыты и правильно вложены (валидный XHTML), и собирает текст заново из разобранных частей, поэтому чужой HTML и скрипты в него не попадают.
- **Предпросмотр.** Сообщение показывается таким, каким его сохранит сервер, без перезагрузки страницы.
- **Ответы.** На любой комментарий можно ответить, ветки раскрываются по уровням.
- **Таблица корневых комментариев.** Сортировка по User Name, E-mail и дате в обе стороны, по умолчанию сначала новые (LIFO). По 25 комментариев на страницу, можно выбрать 10 или 50.
- **Вложения.** Картинка JPG, GIF или PNG уменьшается на сервере с сохранением пропорций до 320×240, анимированный GIF остаётся анимированным. Текстовый файл TXT принимается до 100 КБ. Картинки и файлы открываются в lightbox с анимацией.
- **Живые обновления.** Новый комментарий появляется у всех, кто смотрит на ту же страницу таблицы или ту же ветку, через WebSocket.
- **Капча и токен автора.** После решённой капчи сервер выдаёт JWT, и следующий час тот же автор пишет без капчи.
- **Защита.** Ограничения числа запросов с одного IP, параметризованные запросы к базе, Content Security Policy, проверка содержимого загруженных файлов, а не только их расширений.

## Технологии

| Часть | Что используется |
|---|---|
| Backend | Python 3.12, Django 5.2 и Django ORM, GraphQL (Strawberry), WebSocket (Channels), uvicorn |
| Frontend | React 18, Vite, Tailwind CSS; nginx раздаёт клиент и проксирует API |
| База данных | MySQL: на сервере управляемая MySQL HeatWave в Oracle Cloud, без облака MySQL 8.4 в контейнере |
| Файлы | S3 API (boto3): на сервере Object Storage в Oracle Cloud, без облака SeaweedFS в контейнере |
| Кеш и общее состояние | Redis: кеш страниц и веток, капчи, лимиты с одного IP, слой Channels для рассылки событий |
| Очередь | Celery и RabbitMQ: удаление файлов несохранённых комментариев с повторами |
| Авторизация | JWT (PyJWT) вместо повторной капчи |
| Окружение | Docker и Docker Compose: всё приложение и его окружение в контейнерах |
| Нагрузочные тесты | k6, сценарии и результаты в `perf/` |

## Как устроено

Снаружи открыт один порт, на нём nginx. Он отдаёт собранный клиент, передаёт `/graphql/` и `/ws/` в backend, а `/media/` берёт из бакета и кеширует. Backend работает в двух процессах uvicorn, по одному на ядро сервера. Всё, что процессы должны видеть одинаково (капчи, лимиты, кто какую страницу смотрит, события), лежит в Redis, поэтому событие из одного процесса доходит до сокетов другого. Страницы списка и ветки кешируются в Redis, и новый комментарий сбрасывает только то, что он меняет. Если Redis недоступен, список и ответы читаются из базы, а написать можно только с токеном автора.

Миграции применяет сервис `migrate` один раз перед стартом backend.

## Установка без облака

Нужны только Git и Docker с Compose 2.20 или новее. Скачайте репозиторий и запустите приложение из его папки:

```bash
git clone https://github.com/Otcovsky/Comments.git
cd Comments
docker compose --env-file local/comments.env -f docker-compose.yml -f docker-compose.local.yml up -d --build
```

Приложение откроется на `http://localhost:8080/`. Порт задаёт `HTTP_PORT` в `local/comments.env`. Первый запуск занимает несколько минут: собираются образы и MySQL готовит базу.

Если приложение открывают не на этой машине, а с другой, добавьте адрес, по которому его открывают, в `DJANGO_ALLOWED_HOSTS` в `local/comments.env`, иначе новые комментарии не будут приходить без перезагрузки (подробнее в разделе «Настройки»).

Облачные сервисы здесь заменены контейнерами: `docker-compose.local.yml` добавляет MySQL 8.4 (сервис `mysql`) и S3-совместимое хранилище SeaweedFS (сервис `s3`), а сервис `bucket` один раз создаёт в нём бакет. Код тот же, что на сервере, отличаются только адреса и ключи в файле настроек. Значения в `local/comments.env` и `local/s3.json` подходят только для этой машины. Данные лежат в томах `mysql-data` и `s3-data`. Остановить и удалить их:

```bash
docker compose --env-file local/comments.env -f docker-compose.yml -f docker-compose.local.yml down -v
```

## Установка с облачными сервисами

На сервере база и файлы облачные: управляемая MySQL HeatWave и Object Storage в Oracle Cloud, к которому приложение обращается через S3 API. Остальное (nginx с клиентом, backend, воркер Celery, Redis, RabbitMQ) работает в контейнерах, как и без облака.

1. Создайте базу MySQL с пользователем, у которого есть права на неё, и бакет, из которого объекты можно читать без авторизации.
2. Рядом с папкой проекта создайте `comments.env` по образцу `comments.env.example` и заполните его: `DJANGO_SECRET_KEY`, `DJANGO_ALLOWED_HOSTS`, `DB_*`, `S3_*` и `RABBITMQ_PASSWORD`. Что значит каждая переменная, описано в разделе «Настройки».
3. Из папки проекта:

```bash
docker compose --env-file ../comments.env up -d --build
```

Приложение откроется на порту 80 (`HTTP_PORT` в `comments.env` меняет его). Порты backend, Redis и RabbitMQ наружу не открыты.

## Настройки

Все настройки лежат в одном файле: `local/comments.env` для запуска без облака, `../comments.env` на сервере (образец — `comments.env.example`). Docker Compose читает этот файл дважды. Флаг `--env-file` подставляет значения в `docker-compose.yml`, а `env_file` передаёт их контейнерам backend, воркера и миграций. Переменная, заданная в командной строке, важнее файла: `HTTP_PORT=8081 docker compose ...` откроет приложение на другом порту, а файл останется как был.

`REDIS_URL` и `CELERY_BROKER_URL` в файл не пишут: их задаёт `docker-compose.yml`, потому что Redis и RabbitMQ всегда работают в соседних контейнерах.

### Django

| Переменная | Обязательна | Что задаёт |
|---|---|---|
| `DJANGO_SECRET_KEY` | да | Секретный ключ Django. Из него же выводится ключ подписи JWT автора, поэтому после смены ключа выданные токены перестают действовать и авторы снова решают капчу. Нужна длинная случайная строка, например от `python3 -c "import secrets; print(secrets.token_urlsafe(50))"`. |
| `DJANGO_ALLOWED_HOSTS` | да | Имена и IP-адреса, по которым открывают сайт, через запятую, без схемы и порта: `example.com,89.168.107.87`. По ним backend проверяет заголовок Origin у WebSocket. Если адреса из строки браузера здесь нет, страница работает, но новые комментарии без перезагрузки не появляются. |
| `DJANGO_DEBUG` | нет | `1` включает режим отладки Django. Только для разработки. |

### База данных

| Переменная | Обязательна | Что задаёт |
|---|---|---|
| `DB_HOST` | да | Адрес сервера MySQL. Без облака это `mysql`, имя контейнера. |
| `DB_PORT` | да | Порт MySQL, обычно `3306`. |
| `DB_NAME` | да | Имя базы. Таблицы в ней создаёт сервис `migrate`. |
| `DB_USER`, `DB_PASSWORD` | да | Пользователь backend и его пароль. Ему нужны права на создание и изменение таблиц в этой базе: под ним же идут миграции. |
| `MYSQL_ROOT_PASSWORD` | только без облака | Пароль root в контейнере MySQL. Приложение им не пользуется. |

Соединение с базой всегда шифруется (TLS), поэтому сервер MySQL должен его поддерживать. И MySQL HeatWave, и контейнер MySQL 8.4 поддерживают его сами.

Без облака контейнер MySQL создаёт базу `DB_NAME`, пользователя `DB_USER` и пароли только при первом запуске, когда том `mysql-data` ещё пуст. Если поменять их потом, контейнер их не применит, и backend не подключится. Тогда тома нужно удалить (`down -v`, данные пропадут) и запустить заново.

### Файлы

| Переменная | Обязательна | Что задаёт |
|---|---|---|
| `S3_ENDPOINT` | да | Адрес S3 API хранилища. В Oracle Cloud это `https://<namespace>.compat.objectstorage.<region>.oraclecloud.com`, без облака `http://s3:8333` (контейнер SeaweedFS). Из него и `S3_BUCKET` nginx собирает адрес, с которого отдаёт `/media/`. |
| `S3_REGION` | да | Регион хранилища, например `eu-frankfurt-1`. SeaweedFS регион не важен, там стоит `us-east-1`. |
| `S3_BUCKET` | да | Имя бакета. Объекты в нём должны читаться без авторизации: nginx берёт их без ключей. Без облака бакет создаёт сервис `bucket`. |
| `S3_ACCESS_KEY`, `S3_SECRET_KEY` | да | Ключи S3 API с правом записи и удаления в бакете. В Oracle Cloud это Customer Secret Key пользователя. Без облака они должны совпадать с ключами в `local/s3.json`. |

### Очередь и запуск

| Переменная | Обязательна | Что задаёт |
|---|---|---|
| `RABBITMQ_PASSWORD` | да | Пароль пользователя RabbitMQ. Брокер создаёт этого пользователя при первом запуске, backend и воркер подключаются под ним. Без пароля Compose не запустится. Как и с MySQL, новый пароль применяется только к пустому тому `broker-data`. |
| `RABBITMQ_USER` | нет, `comments` | Имя этого пользователя. |
| `BACKEND_WORKERS` | нет, `2` | Число процессов uvicorn в backend, по одному на ядро сервера. |
| `HTTP_PORT` | нет, `80` | Порт на машине, на котором открывается приложение. В `local/comments.env` это `8080`. Если порт занят, задайте другой. |
| `COMMENTS_ENV_FILE` | нет, `../comments.env` | Какой файл настроек получают контейнеры. В `local/comments.env` указывает на сам этот файл; на сервере его не задают. |

### Только для нагрузочных тестов

Для живых пользователей их не задают. Как ими пользоваться, описано в `perf/README.md`.

| Переменная | Что задаёт |
|---|---|
| `CAPTCHA_TEST_ANSWER` | Ответ, который получает каждая капча, чтобы k6 мог писать комментарии. Капча по-прежнему одноразовая. |
| `RATE_LIMIT_EXEMPT` | Сеть, например `10.0.0.0/24`, запросы из которой не ограничиваются ни в nginx, ни в backend: вся нагрузка идёт с одной машины. |
| `DB_POOL_REPORT` | Раз в столько секунд backend пишет в лог, сколько запросы ждали свободного потока к базе. `0` выключает. |
